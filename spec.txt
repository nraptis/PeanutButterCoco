PBTR typed record format draft

Purpose
- Use one binary typed-record grammar for both:
  - the optional public preview manifest
  - the authoritative archive payload stream
- Keep stream records container-agnostic.
- Keep normal decode naive and forward-moving.
- Make repair a separate mode that can replace bad or missing data blocks with repair copies.

Current proposed defaults
- max path length: 16384 bytes
- max archive count: 1048576 archives
- path length field: little-endian 16-bit unsigned integer
- file size field: little-endian 64-bit unsigned integer
- archive headers remain fixed-size 64-byte structural headers
- section headers remain fixed-size 96-byte structural headers

In-stream record grammar
- There are only 4 record types:
  - manifest file
  - manifest folder
  - data file
  - data folder
- Record shape:
  - path_length_le16
  - path_bytes[path_length]
  - type_flag_u8
  - if type_flag is a file type: file_size_le64
- `type_flag_u8` is the content-type discriminator for the logical record.
- `file_size_le64` always means logical file size for file records, including preview-manifest file records.
- Folder records do not carry a file-size field.
- The same typed-record decoder should be able to parse preview-manifest records and payload-stream records without branching on a second grammar.
- Files and folders may be inter-mixed in the data zone.
- Record writers should be ignorant of where they are in a payload stream.
- Records do not encode:
  - end of block
  - end of section
  - end of archive file
  - end of archive family

Encoding and path rules
- path_bytes are stored on disk as UTF-8.
- This supports Chinese, Russian, English, German, and other Unicode path names.
- Platform UTF-16 paths are supported by transcoding at the platform boundary into UTF-8 before storage.
- Validation happens on decoded path parts, not on individual raw continuation bytes.
- UTF-8 continuation bytes are not separators or traversal markers by themselves.
- Raw NUL bytes are forbidden inside path_bytes.
- path_length must be in [1, mMaxPathLength].
- Paths must be relative.
- Exact path parts "." and ".." are forbidden.
- Names like "a..", "..a", and "a.a" are allowed because they are not exact traversal segments.
- Empty path parts are forbidden.
- Drive-letter roots are forbidden.

Stream versus container rules
- Records live in a stream.
- Blocks own their boundaries from the outside.
- Sections own their byte budgets from the outside.
- The orchestrator decides:
  - how many manifest blocks exist
  - how many data blocks exist
  - how many repair blocks exist
  - what zone comes next after a block finishes
- The record parser should not need to know whether packing was tight or sparse.
- Sparse mode is an orchestration rule, not a second record grammar.
- Sparse packing may choose to pre-separate folders from file payload before writing.
- That pre-separation is a pack-time execution choice, not a decode-time grammar fork.
- Variable-length payload may cross block boundaries.
- Fixed-width structural scalars must not cross block boundaries.
- Hardline: all fixed-width scalars are block-local.
- Writers must leave sufficient tail padding so no scalar begins unless it fully fits in the remaining block payload.
- Unused tail bytes are zero-filled.

Block-level section planning
- The archive still plans block-level zones at planning time.
- Archive boxes should be able to store at least:
  - `mManifestBlockCount`
  - `mDataBlockCount`
  - `mRepairBlockCount`
  - whether the physical file is present
  - whether the physical file is readable
- These counts are local per-box planning promises, not family-level extraction authority.
- This is what allows decode to know how many blocks of each kind are expected while still keeping record writers container-agnostic.

Section-header redundancy
- Every section header carries the full checked bootstrap set, even if some fields are unused for that section type.
- This redundancy is intentional.
- The goal is to let a section header bootstrap repair and discovery even when the archive header is missing or unreadable.
- The section header size is 96 bytes.
- Recommended packed layout:
  - checksum: 32 bytes
  - skip record: 7 bytes
  - repair record: 8 bytes
  - section type: 1 byte
  - section flags: 1 byte
  - payload bytes used: 4 bytes
  - archive file count: 4 bytes
  - archive block count in this physical archive file: 4 bytes
  - this archive index: 4 bytes
  - this block index: 4 bytes
  - archive data block count: 4 bytes
  - preview manifest block count: 4 bytes
  - folder manifest block count: 4 bytes
  - repair data block count: 4 bytes
  - archive family id: 8 bytes
  - reserved padding: 3 bytes
- A 96-byte section header is acceptable overhead because:
  - it divides cleanly by 16
  - it keeps all bootstrap geometry in one place
  - it is still tiny relative to multi-megabyte block payloads
- Skip metadata is always present because re-finding file starts must not require replaying large decrypt spans.
- `mPayloadBytesUsed` is the authoritative count of meaningful payload bytes in the current block.
- Decode must not read beyond `mPayloadBytesUsed` for that block.
- This removes the need for a sparse-padding "has next record" flag as a decode truth source.
- `mArchiveBlockCount` means the local block count for this physical archive file, not the total family block count.
- `mSectionType` remains stored even though zone geometry may also imply it.
- Keeping `mSectionType` is intentional redundancy:
  - it gives decode one more cross-check
  - it helps catch mismatched or improperly packed blocks

Manifest meanings
- Public preview manifest:
  - optional
  - binary
  - advisory visibility metadata
  - may include file sizes for preview file records
  - must not drive extraction decisions
- Manifest-zone records inside the real archive stream:
  - authoritative
  - mainly useful for sparse mode
  - decoded with the same typed-record grammar as everything else
  - may contain tightly packed folder records in sparse execution

Packing execution modes
- Compact execution may inter-mix file and folder records directly in the data zone.
- Sparse execution may separate folders from file payload before packing.
- In sparse execution:
  - folder records may be packed tightly into manifest-zone blocks
  - file payload records still use the same typed-record grammar
  - this is a separate packing execution, not a separate decode format
- Decode and Recover should not need branch logic for:
  - folder manifest
  - archive data sparse
  - archive data compact
- Decode and Recover should only need zone ownership and typed-record semantics.

Sources of truth
- File name is first for slot claim.
- Archive header is second only for local geometry hints, local block-count hints, family-id hints, finalization state, and anomaly repair.
- Public preview manifest is never authoritative for extraction.
- Recommended hardline rule:
  - a physical file claims a box slot by filename template first
  - headers may confirm, enrich, or disagree
  - headers do not get to silently move that file into a different slot except under the explicit anomaly-repair rule below
- Stronger wording:
  - filename decides which logical box a file belongs to
  - a readable header may describe that file's own internal layout
  - a header does not get to redefine the family window by itself
  - a header does not get to force extraction to stop merely because its family-wide count claim looks scary

Archive box model
- Archive boxes are the logical slots in the discovered family window.
- A box may contain:
  - a physical archive file
  - a damaged physical archive file
  - no physical archive file at all
- A box with no physical file is a gap-archive.
- Build archive boxes in this order:
  - gather filename-template candidates
  - assign provisional box slots by filename
  - deduplicate competing files for the same slot
  - choose a dominant family id from readable headers when possible
  - derive accepted archive count from readable headers:
    - if there is exactly 1 readable archive header, treat that archive count as accurate
    - if there are 2 or more readable archive headers, treat the majority-vote count as accurate
    - if there is no readable archive header, use only the filename-discovered span for now
  - run anomaly repair using header index only when needed
  - instantiate the family window
  - attach per-box local planning hints from each readable header
- The family window should preserve logical slot positions so later payload does not slide left when a middle archive is missing.
- Missing files inside the instantiated window become gap-archives, not instant hard failure.
- The window may grow later only if a stronger source earns that right:
  - another discovered filename-template match outside the current window
  - authoritative manifest-zone records decoded from trusted archive payload
- Accepted archive count may extend the instantiated window so Recover preserves expected gap positions.

Archive placement rule
- There are exactly 2 ways for a physical archive file to land in an archive box:
  - filename-derived slot
  - header-index-derived slot
- Filename-derived slot is always the provisional placement.
- Header-index-derived placement is allowed only as anomaly repair.
- Anomaly repair is allowed only when all of the following are true:
  - the header index is readable and in range
  - the filename-derived slot is impossible, contradictory, or lower-confidence under the accepted archive count
  - the header-index-derived slot produces a more self-consistent family mapping
- A filename-derived slot is considered impossible or contradictory when, for example:
  - it lies outside the accepted archive-count range
  - it collides with a stronger incumbent and the header-index placement resolves that collision cleanly
  - it implies a broken family shape that the header-index placement repairs
- If both filename slot and header index are plausible, keep the filename slot.
- Header index must not silently displace a stronger incumbent.
- If header-index repair would collide with an already stronger occupant, keep the existing occupant and mark the incoming file anomalous.
- Example:
  - discovered files: `archive_0000.zip`, `archive_0004.zip`
  - both readable headers say archive count = `2`
  - `archive_0004.zip` header index = `1`
  - provisional filename slots are `0` and `4`
  - accepted archive count is `2`, so valid box range is `0..1`
  - slot `4` is impossible under that accepted count
  - reassign `archive_0004.zip` to slot `1` by header-index anomaly repair
  - final mapping is box `0` and box `1`

Header-count handling
- Accepted archive count is derived this way:
  - if exactly 1 readable archive header exists, use its archive count as accurate
  - if 2 or more readable archive headers exist, use the majority-vote archive count as accurate
  - if no readable archive header exists, there is no accepted header-derived archive count yet
- Once accepted archive count exists, Recover may derive expected family geometry from it, including:
  - expected archive count
  - expected preview manifest block count
  - expected folder manifest block count
  - expected data block count
- Those accepted expectations are what allow gap archives to exist without shifting later logical payload left.
- Header disagreement that loses the one-header rule or majority vote does not become family truth.
- A minority or unreadable header may still contribute local per-box hints if its local geometry is readable.
- This preserves classic gap behavior:
  - pack 10 archives
  - delete archive 6
  - accepted archive count remains 10
  - recovery still materializes box 6 as a gap-archive
  - archives 7..10 keep their original logical positions
  - later file starts are not shifted left into the missing slot
- One-file safety rule:
  - if the lone readable archive says archive count is 1, treat that as accurate
  - if the lone readable archive says archive count is huge, treat that count as accurate for expected geometry, but still do not let missing later boxes become immediate fatal truth by themselves
  - the cost of a bad lone header is diagnostic noise and extended gap expectation, not slot collapse or forced early failure
- Once authoritative manifest-zone records are decoded from trusted payload, they may confirm, narrow, or override the softer header-derived expectation about how many logical files were originally packed.

Inspection phase
- Archive-family work now has 2 early phases:
  - Discovery
  - Inspection
- Discovery:
  - find physical files
  - assign provisional archive boxes
  - read archive headers when possible
- Inspection:
  - read enough section-header truth to refine archive boxes and bootstrap geometry
  - this is allowed because section headers are now self-describing enough to add trusted information
  - for encrypted non-preview data, practical implementation may need the cipher assembled before section-header inspection can succeed
- Unbundle inspection rule:
  - try to decode the first block in the first archive
  - if that first-block inspection fails, Unbundle fails
- Recover inspection rule:
  - keep walking forward until a valid block is found
  - once a valid block is found, use its section-header truth to refine the archive boxes
  - throw away any speculative decoded content from the inspection pass
  - then start the real recovery job
- Inspection should refine archive boxes explicitly.
- Inspection should not silently replace Discovery as the first phase.

Optimistic and pessimistic walking
- Decode starts optimistic.
- In optimistic mode, the reader may rely on:
  - archive box planning
  - per-box planned block counts from readable local headers
  - planned section counts that are locally validated as the walk advances
- Once the walk reaches a real disagreement, decode may switch to pessimistic mode.
- Real disagreements include:
  - missing file at a required box
  - impossible physical length for planned blocks
  - section-type disagreement against planned block counts
  - corrupt header data that breaks required geometry
- In pessimistic mode:
  - stop trusting further forward-looking promises
  - keep walking with what the physical files and validated local structure actually provide
  - fail only when the walk reaches a concrete structural impossibility
- Recover must be able to keep walking across valid records even when logical content order is unusual or damaged.
- Out-of-order surviving content is a recovery reality, not a reason to introduce a second record grammar.

Block continuity
- Decode should keep track of the previous archive/block position for the current logical file.
- Decode should also know the expected next archive/block position for continued file content.
- If the next physically decoded block is not a legal successor for the currently open file, decode must stop appending to that file.
- This prevents dumping correct-looking bytes from the wrong block into the wrong output file.
- `mPayloadBytesUsed` helps here by making the block's real payload span explicit before continuity decisions are made.

Sparse expectations
- "We expected more files" may begin as a soft anchor-header expectation during recovery.
- The preferred strong source is authoritative manifest-zone payload decoded from trusted archive data.
- This allows sparse jobs to report both truths at once:
  - extraction reached the end of the physically available family window
  - the original packed job described more logical files than were physically present here
- Before authoritative manifest-zone evidence exists, the decoder may report only weaker statements:
  - the anchor header expected more archive boxes
  - header hints disagree
  - recovery continued with partial physical evidence

Skip record rules
- Skip records are for repair mode.
- Their main semantic purpose is to re-find a file start.
- They are not general semantic truth.
- Normal unbundle must not depend on skip records for correctness.
- Repair may honor a skip record after damage is detected.
- A zero skip means "no jump".
- Invalid skip records are ignored and logged.

Skip target rules
- Skip distances are payload distances, not raw-file byte offsets.
- The reader does not reason in terms of "jumping into an archive header" or "jumping into a section header."
- If skip math is payload-relative, those cases should be impossible by construction.
- The only meaningful skip failures are:
  - the target goes beyond available physical payload
  - the target goes outside the logical box window
  - the target exceeds configured numeric limits
- If a skip target lands in a gap-archive during repair:
  - continue the repair walk forward
  - transition partial file handling into the explicit partial-file flow

Repair behavior
- Repair is block replacement first, not merely tolerant decode.
- Bundle-time repair coverage options are:
  - `25%`
  - `50%`
  - `75%`
  - `100%`
- The chosen repair percentage means:
  - for each archive file, count its non-repair blocks
  - multiply by the chosen percentage
  - round up to the nearest whole block
  - emit exactly that many repair-copy blocks for that archive
- Repair-copy ordering is front-of-archives by layer.
- Example with 4 archives each containing 4 non-repair blocks:
  - archive A: `a1 a2 a3 a4`
  - archive B: `b1 b2 b3 b4`
  - archive C: `c1 c2 c3 c4`
  - archive D: `d1 d2 d3 d4`
- At `25%`, the repair zone is:
  - `a1 b1 c1 d1`
- At `50%`, the repair zone is:
  - `a1 b1 c1 d1 a2 b2 c2 d2`
- These repair-copy blocks are exact copies of the source archive blocks taken from the fronts of the archive files.
- A valid family may contain repair blocks even when there is only one archive file.
- Example:
  - one small image
  - one data block
  - one repair block for that one data block
  - still valid
- Repair discovery should stay dumb and local:
  - walk archives backward
  - if the first encountered block of an archive is a repair block, treat that archive as participating in the repair walk
  - if the first encountered block of an archive is not a repair block, allow that one transition and then sweep that archive block-by-block
  - after that archive sweep finishes, stop the backward repair discovery
- This avoids needing a family-wide "repair records present" promise in headers.
- Repair discovery does not require all later archives to be homogeneous.
- Example weird but valid shape:
  - archive 34 has repair records
  - archives 35 through 8999 have no repair records
  - archives 9000 through 90210 have repair records
  - a backward repair walk may still stop cleanly once it reaches the first non-repair-first archive and sweeps it
- Repair ordering uses 2 cursors:
  - discovery cursor
  - target cursor
- Discovery cursor rules:
  - the discovery cursor walks archive headers, section headers, and repair blocks in physical repair-walk order
  - the discovery cursor is the only cursor that decides which repair record is encountered first
  - discovery ordering must remain stable even after a repair record later points somewhere else
- Target cursor rules:
  - the target cursor is spawned only after a repair record has been successfully decoded
  - the target cursor validates or reads the pointed-to target archive and target block
  - target-cursor failures do not reorder discovery-cursor history
- This keeps repair blocks ordered:
  - repair records are encountered in discovery order
  - target validation happens after each repair record is decoded
  - jumping to a target does not change which repair record counts as "next"
- Recommended repair rule:
  - try the original data block
  - if the original data block validates, use it
  - if the original data block fails and the repair block validates, substitute the repair block
  - if both fail, continue the repair walk
- The simplest integrity rule is to make the original block and repair block validate under the same checksum semantics.
- Repair may still use skip hints to re-find file starts after substitution or after unrecoverable damage.
- Repair is allowed to create missing archive files when necessary for recovery.
- Those created files may be synthesized as zero-filled files sized from trusted section-header and family geometry.
- If Repair determines that an archive file must reach an exact size and the current physical file is too small:
  - grow it to that exact size
  - zero-fill the missing tail
- If the current physical archive file is already larger than the exact required size:
  - do not shrink it
- This is one reason section headers carry both:
  - `mArchiveFileCount`
  - `mArchiveBlockCount`
- In normal Unbundle:
  - unexpected file end is an error
  - Unbundle does not synthesize missing archive files just to continue

Security fences
- Fences matter for:
  - path parsing
  - folder parsing
  - file-size parsing
  - file-content parsing
  - repair walking
- Distinguish the data zone from the repair zone.
- A fence is any point where the decoder must stop interpreting payload for the current zone:
  - zone boundary
  - physical readable end of file
  - configured payload boundary
- Fence violations should block interpretation.
- Fence violations do not automatically mean the whole family is dead.
- In recovery mode:
  - bad skip target -> ignore it and continue forward
  - bad path length -> ignore this damaged block and continue forward
  - bad content length -> ignore this damaged block and continue forward
- In normal decode mode:
  - the moment an invalid path length or invalid content length is reached is the moment of failure

Tail hygiene
- Our obligation is to fill trailing tails with zero after real data writing is done.
- Our obligation is not to pre-zero blocks before writing starts.
- Conservative validation and tests may verify that tail bytes are zero.
- Non-zero tail bytes are conservative validation failures, not necessarily customer-facing public errors.

Dangling-state failures
- The stream is invalid if the available payload ends while decoding is in the middle of:
  - a path-length field
  - path bytes
  - a type flag
  - a file-size field
- A file record is invalid if its declared payload never completes.
- Clean block boundaries come from outer block ownership and orchestration, not from inner block-end records.
- The record parser is allowed to continue across blocks.

Partial output policy
- Partial outputs must never be silently presented as complete customer data.
- Writes should be visible in the destination folder while extraction is happening.
- During active write, the destination name should be prefixed with `$WRITING_`.
- If `$WRITING_name.txt` collides, use a visible collision form such as `$WRITING_name_1.txt`.
- On successful completion, atomically rename:
  - `$WRITING_name.txt` -> `name.txt`
  - `$WRITING_name_1.txt` -> `name_1.txt`
- On incomplete or damaged completion that is being preserved, rename:
  - `$WRITING_name.txt` -> `$PARTIAL_name.txt`
  - `$WRITING_name_1.txt` -> `$PARTIAL_name_1.txt`
- Complete files and partial files must never share the same final visible name.
- Recovery and cancel flows must leave behind either:
  - a complete final name
  - or a clearly marked `$PARTIAL_` name
  - but never a misleading apparently-complete truncated file

Impossible sizes and allocation limits
- Readers must not allocate memory proportional to declared file size.
- All file content must be streamed.
- Every arithmetic step that combines archive index, block index, byte offset, path length, or file size must be overflow-checked.
- Readers must reject sizes or distances that exceed configured policy limits before opening output files.
- Use explicit policy limits instead of a generic public "arithmetic overflow" outcome whenever possible.
- Suggested named limits:
  - `MAX_CONTENT_LENGTH = 2305843009213693952`
  - `MAX_STRIDE_LENGTH = 2305843009213693952`
- Suggested limits:
  - max path length: 16384
  - max archive count: 1048576 by default, configurable
  - max blocks per archive: configured and finite
  - max per-file extracted bytes: configured and finite
  - max total extracted bytes per operation: configured and finite

Disk safety
- Extraction must never escape the destination root.
- Parent directories must be created only inside the destination root.
- Recovery and cancel flows must not leave behind unrelated truncated customer files.
- Incomplete files may be preserved only if they are clearly marked partial.
- Nothing in the manifest may cause deletion or overwrite outside the chosen destination root.

Privacy
- Public preview visibility is a privacy decision, not just a convenience feature.
- The default preview policy should stay conservative in encrypted mode.
- Full paths and exact sizes in logs are metadata leaks and should be policy-controlled.
- No extra buffer-scrubbing requirements are being imposed in this draft.

Error modes
- Public error modes should describe what kind of outcome the customer hit.
- Internal detail should be richer than the public code.
- Recommended public code families:
  - canceled
  - invalid request
  - file system
  - crypt
  - family discovery
  - header validation
  - block integrity
  - record parse
  - unsafe path
  - size limit
  - recovery exhausted
  - internal
- Errors are emitted when the walk first encounters a provable failure.
- "Encounters" means the read-head has advanced far enough to prove the failure against the bytes and fences available at that moment.
- The decoder must not emit an error early just because a later contradiction is now suspected.
- The decoder must not delay an error once the current read-head position already proves it.
- The default rule is dumb and deterministic:
  - the earliest provable failure in walk order wins
  - once that failure is emitted for the current parser event, later dependent failures from that same event are not also emitted
  - if two checks are possible, emit the one whose proof point the read cursor reached first
- Universal precedence rule:
  - size / under-read failures supersede later semantic failures for the same parser event
  - once a parser event is known to lack enough readable bytes, do not also emit later semantic or pointer errors from that same event
- Size / under-read precedence applies immediately when:
  - an archive header is reached without enough bytes to support a full archive header
  - a section header is reached without enough bytes to support a full section header
  - a block body is reached without enough bytes to support a full planned block body
- These size failures should not be simultaneous with later semantic failures from the same parser event.
- Example:
  - if a repair record archive pointer is proven invalid before its block pointer is even interpreted, emit the archive-pointer error and stop that repair-record parse
  - if a path decodes and the first forbidden exact part is `..`, emit the unsafe-path error at the first byte position where that forbidden part became knowable
  - if a section header is too short, emit the section-header under-read error and do not also emit unknown-section-type from that same truncated header
- Recovery may continue after emitting recoverable errors.
- Normal decode may fail immediately after emitting the errors that became provable at that walk position.
- The stack should now follow code-perspective usefulness rather than byte-order purity.
- If a validation routine naturally proves several same-scope errors together, it may emit that set together.
- Archive-header validation may therefore emit multiple archive-header errors at once.
- Section-header validation may therefore emit multiple section-header errors at once.
- The goal is:
  - useful debugger information
  - useful test assertions
  - not a fake "one byte at a time" purity rule

Error stack
- The system should support an error stack, not a single flat error.
- Proposed model:
  - `ErrorInfo`
    - `error_code`
    - `message`
    - `walk_offset`
    - `field_start_offset`
    - `file_loc`
    - `record_state`
  - `ErrorData`
    - `errors: [ErrorInfo]`
- `walk_offset` is the payload-relative byte position where the walk first had enough evidence to emit that error.
- `field_start_offset` is the payload-relative byte position where the failing parser event began.
- `file_loc` identifies which outer region the walk was in, such as:
  - archive header
  - section header
  - preview manifest
  - folder manifest
  - data zone
  - repair zone
- `record_state` should identify the parser stage being evaluated, such as:
  - path length
  - path bytes
  - type flag
  - file size
  - file content
  - skip target
  - fence check
- The error stack should preserve emission order.
- Each emitted `error_code` should already be specific enough for debugging and tests.
- Avoid a second free-form `sub_error` layer unless a code family truly needs it.
- A validation routine may append multiple same-scope codes if that is the natural code-level output of the check.
- Emit what actually tripped the program up in code terms.
- Tests should be able to assert on:
  - the ordered full error stack
  - the public error code family
  - the precise specific code
  - the walk offset where each error was emitted
- Public code families are for customer-facing outcome buckets.
- Specific codes are for debugger clarity and tests.

Specific code structure
- Recommended format:
  - `LOCC_TTT_NNN_Name`
- Meaning:
  - `LOCC` = file-location family
  - `TTT` = error-type family
  - `NNN` = stable sequence number
  - `Name` = short mnemonic
- Recommended file-location families:
  - `ARHD` = archive header
  - `SECH` = section header
  - `PRVW` = preview manifest
  - `FOLD` = folder manifest
  - `DATA` = data zone
  - `REPR` = repair zone
  - `SYS` = system / runtime / OS interaction
- Recommended error-type families:
  - `UND` = under-read / not enough readable bytes for required structure
  - `INV` = invalid data or invalid enum
  - `NUM` = invalid number or out-of-policy number
  - `FNC` = fence or boundary violation
  - `PTR` = pointer / target problem
  - `CHK` = checksum / integrity failure
  - `PTH` = unsafe or invalid path
  - `IOP` = system I/O or persistence failure

Repair pointer precedence example
- If a repair record contains an invalid archive pointer and an invalid block pointer:
  - emit `REPR_PTR_002_ArchivePointer` if the archive pointer is the first failing field encountered by the walk
  - do not continue to emit `REPR_PTR_003_BlockPointer` from that same broken repair-record parse unless parsing can continue independently and truthfully

Error classification by file-location
- Archive header:
  - family identity disagreements
  - archive count and index number errors
  - fixed-size header fence failures
- Section header:
  - unknown section type
  - impossible section size or stride
  - header crossing physical end
- Preview manifest:
  - invalid preview record type
  - invalid preview path
  - preview file-size errors
- Folder manifest:
  - invalid folder path
  - forbidden traversal parts
  - path fence failures
- Data zone:
  - path length, type flag, file size, file content, and tail-padding errors
- Repair zone:
  - repair pointer, skip target, repair checksum, and target-window errors

Errors that do not overlap under the current first-hit rule
- forbidden traversal part does not overlap with any later semantic path error, because it emits at the first byte position where that exact invalid part becomes knowable
- unknown type flag does not overlap with file-size or file-content errors from the same record
- archive pointer error does not overlap with block pointer error from the same repair-record parse if archive pointer is encountered first
- scalar-starts-in-short-tail does not overlap with successful scalar parse
- under-read header errors do not overlap with later semantic header errors from that same truncated structure
- under-read block-body errors do not overlap with later inner-record parse errors from that same incomplete planned block
- payload-bytes-used-too-large does not overlap with later inner-record parse errors from that block, because the block span itself is already invalid
- block-continuity mismatch does not overlap with further file append success for that same continuation decision

Errors that can still coincide only if they arise from separate parser events at the same walk position
- a current record error and an already-preserved prior warning may both exist in the stack
- independent outer-structure validation and inner-record validation may both be logged only if both truths are reached without speculative continuation
- multiple same-scope archive-header or section-header validation codes may be emitted together if the validation routine proves them together

Collision list
- Low-risk collisions:
  - outer archive-box planning warning + later local record error
  - section-header warning + first inner-record error after section entry
  - recoverable repair warning + later data-zone parse error
- Medium-risk collisions:
  - section-header boundary issue discovered at the same read-head where the first inner record also becomes impossible
  - non-zero tail padding found at the same point a scalar would otherwise have started in short tail
  - file-size policy failure discovered at the same point physical content continuation also becomes impossible
- Worst-case nightmare scenarios for the error stack:
  - a damaged repair archive where:
    - the archive family already has planning warnings
    - the current repair record has a questionable target
    - the enclosing section is near its fence
    - the physical file ends early
    - and the output write also fails
  - hardline rule:
    - only one parse-local first-hit code is emitted for the broken repair-record parse
    - outer already-known warnings may remain earlier in the stack
    - later system failure may be appended if it truly occurs during output handling
    - do not recursively explode one broken parse into five sibling codes
  - a data record whose path ends near block tail, next scalar cannot fit, tail bytes are non-zero, and the destination path would also be unsafe
  - hardline rule:
    - if the unsafe path became knowable first, emit the path error
    - if scalar-starts-in-short-tail became knowable before path semantics were complete, emit the short-tail scalar error
    - non-zero tail padding may stand alone only if the parser is already in tail-padding interpretation state
    - never emit all three just because all three feel "true" in hindsight
  - a tiny truncated archive header file where the filename slot also disagrees with the would-have-been header index
  - hardline rule:
    - emit `ARHD_UND_001_HeaderTooShort`
    - do not also emit index disagreement because the index was never truthfully readable
  - a repair walk where:
    - archive header read succeeds
    - section-header scanning loops until a repair section is found
    - the repair record later points out of fence
    - the pointed-to target block is also bad
  - hardline rule:
    - discovery cursor emits only the first provable failure at each discovery step
    - target-cursor failure is logged only after the repair record itself has been decoded successfully
    - target-cursor failure must not reorder which repair record was "encountered first"

Remaining inconsistency inside error handling
- Non-fatal warnings should share the same ordered stack as hard errors when they come from the same code path and are useful for debugging or tests.
- A separate warning list is no longer preferred.

New inconsistency introduced by the current rules
- Every specific code should map one-to-one onto exactly one public code family.
- Inspection is now an explicit phase, so section-header truth refining archive boxes is no longer a dangling fallback idea.

Error collision candidates
- The spec allows overlapping errors only when the same walk position proves multiple independent failures.
- Expected collision shapes include:
  - path length exceeds max
  - path length crosses fence
  - declared file size exceeds configured extraction limit
  - declared file size crosses fence
  - skip target overflows
  - skip target leaves logical window
  - path decodes successfully but contains a forbidden exact part such as `..`
- Collisions are most plausible in these pairings:
  - path length exceeds max + path length crosses fence
  - file size exceeds policy limit + file size crosses fence
  - skip target overflows + skip target leaves logical window is usually not a true double-report
  - unknown type flag + later file-size problems is usually not a true double-report because file-size parsing should not begin once type is unknown
- Preferred hardline:
  - emit all independently provable errors at the current walk position
  - do not emit derivative or speculative follow-on errors that depend on already-aborted parsing state
  - prefer one narrower sub-error over many noisy synonyms for the same proven fact

Notes
